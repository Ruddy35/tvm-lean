# Передача проекта: формальная модель TVM на Lean 4

Документ для разработчика, который продолжает работу. Он построен по уровням: каждый следующий
раздел углубляет предыдущий. Прочитав разделы 1–4, вы понимаете, что это и зачем. Прочитав всё —
можете работать.

Дата передачи: 2026-10-19. Ветка: `formal-tvm`, коммит, на котором выполнена последняя полная
проверка, — `014e719` (поверх него только этот документ).

---

## 1. За две минуты

- **Что это.** Модель виртуальной машины блокчейна TON (TVM) на языке Lean 4 — исполняемая
  спецификация, которая должна вести себя **ровно так же**, как C++-реализация TVM.
- **Зачем.** Чтобы на её основе формально доказывать свойства любого смарт-контракта TON по его
  байткоду: «инвариант I сохраняется при любой транзакции». Модель — фундамент; если она хоть в
  чём-то расходится с C++, доказательства о ней ничего не говорят о настоящей сети.
- **Основа не наша.** Мы взяли открытый проект `Gusarich/tvm-lean` и дорабатываем его в своей
  ветке. Он **не является истиной**: в нём находились и исправлены ошибки. Истина — C++-код TON
  конкретного коммита.
- **Как проверяем «один в один».** Каждое поведение модели сравнивается с C++ на одних и тех же
  входах: случаи оракула (C++ запускается через `fift`), случайные (fuzz) случаи, исчерпывающая
  проверка декодера на всех 2²⁴ опкодах, повторы реальных прогонов контракта. Сейчас всё проходит.
- **Где мы.** Декодер инструкций доказанно совпадает с C++ на всём пространстве опкодов. Идёт фаза
  2 — «измеримое один в один»: у всех инструкций, кроме 50 криптографических, есть тесты против
  C++, найдено и исправлено полтора десятка ошибок исходной модели. Впереди — криптография, старые
  глобальные версии, фазы транзакции и только потом доказательства о контрактах.

## 2. Цель проекта

Конечная цель — **проверять смарт-контракты TON формально, по байткоду, методом индукции**:

1. Начальное состояние контракта удовлетворяет инварианту.
2. Любая транзакция, переводящая состояние, удовлетворяющее инварианту, сохраняет его.
3. Значит, инвариант верен всегда.

Для этого нужна модель TVM, о которой можно доказывать (Lean 4) и которая совпадает с настоящей
машиной во всём, что наблюдаемо: результат, исключение, код выхода, **израсходованный газ** (это
деньги), состояние `c4` (данные контракта) и `c5` (исходящие действия).

Работа разбита на две стадии, строго по порядку:

| Стадия | Содержание | Состояние |
|---|---|---|
| I. Полная модель | всё, что исполняется при обработке транзакции, на Lean, совпадает с C++ | идёт |
| II. Индукция и инварианты | общая теорема индукции по транзакциям, символьное исполнение байткода с доказанной корректностью, сведение проверки контракта к условиям для решателей | не начата |

Важное решение, принятое по ходу: сначала мы доказывали свойства конкретного контракта (TON
Storage) прямо на модели — получилось 747 теорем, — но это не масштабируется и опирается на модель,
в которой потом нашлись ошибки. Поэтому работа над контрактами отложена (архив, см. раздел 9), а
все силы — на полноту и точность модели.

## 3. Источник истины: C++ и глобальные версии

### 3.1. Эталон

**Истина — исходный код C++ репозитория `ton-blockchain/ton` на коммите
`3d478cbde854be03a18ab2a59f8fc3c565cf7d14`** (2026-08-17, релиз v2026.08). Ровно из этого
коммита собран `fift`, которым пользуется оракул (`fift -V` печатает этот хэш). Все обоснования
изменений модели ссылаются на код этого коммита: файл, функция, строка.

Основные места в C++:

| Что | Где |
|---|---|
| Исполнение инструкций | `crypto/vm/*ops.cpp` (`arithops`, `cellops`, `contops`, `dictops`, `stackops`, `tonops`, `tupleops`, `debugops`) |
| Таблица декодирования, газ за инструкцию | `crypto/vm/opctable.cpp` (`OpcodeInstr*::dispatch`), `cp0.cpp` |
| Цикл VM, исключения, газ | `crypto/vm/vm.cpp`, `vm.h` |
| Словари | `crypto/vm/dict.cpp` |
| Ячейки, срезы | `crypto/vm/cells/` |
| Фазы транзакции | `crypto/block/transaction.cpp` |

Правило: **если модель, тест или документация расходятся с C++, прав C++.** Это касается и тестов
исходного проекта — некоторые из них закрепляли неверное поведение (раздел 6.3).

### 3.2. Глобальные версии

Сеть TON имеет **глобальную версию** (параметр конфигурации 8, в C++ — `VmState::global_version`).
Одна и та же программа ведёт себя по-разному в разных версиях:

- **инструкции появляются с какой-то версии**: `->require_version(N)` в регистрации C++ (89
  инструкций, версии 4–12). Ниже своей версии инструкция — недопустимый опкод;
- **поведение инструкций меняется**: проверки `get_global_version() >= N` в коде исполнения
  (например, с версии 13 `QPOW2` вне диапазона даёт NaN вместо исключения; с версии 14 повторная
  установка регистра управления — тихая пустая операция);
- **фазы транзакции** тоже зависят от версии (`transaction.cpp`).

Опись всех 208 проверок версии в C++ — `docs/audit/cpp-global-version.csv`, разбор —
`docs/audit/README.md`, раздел 3.

**Модель сейчас поддерживает версии 13 и выше** (`VmState.globalVersion`, по умолчанию 13). Все
33 проверки уровня VM с порогом ≥ 13 в модели есть. Сверка с C++ идёт на версиях **13 и 16** (16 —
`SUPPORTED_VERSION` эталонного релиза). Версии ниже 13 — отдельная фаза (раздел 8).

## 5. Как устроена проверка «один в один»

Модель запускается рядом с C++ на одинаковых входах, сравнивается всё наблюдаемое.

| Вид проверки | Что сравнивает | Объём | Где |
|---|---|---|---|
| Unit-тесты | поведение модели с ожиданиями, записанными в тесте (без C++) | 5967 | `Tests/Instr/*/*.lean`, поле `unit` |
| **Оракул** | модель и C++ (`fift runvmx`) на заданных программе, стеке, `c7`: код выхода, газ, весь стек, хэши `c4`/`c5` | 29 844 случая × 2 версии | поле `oracle`; `Tests/Harness/OracleHarness.lean`, `oracle/fif/` |
| **Fuzz** | то же, на случайных входах из генераторов наборов | 405 676 случаев × 2 версии | поле `fuzz`; `Tests/Harness/FuzzHarness.lean` |
| Дифференциальные прогоны | модель против записанных прогонов C++ реального контракта (TON Storage) | 35 889 | `TvmLean/Validation/Diff/`, `~/ws/fixtures` |
| Аудит декодера | длина и допустимость каждого 24-битного опкода (2²⁴ × 2 хвоста) против таблицы C++; тождество инструкции через пересборку | 33,5 млн | `tools/audit/decoder/` |
| Покрытие C++ | какие строки и ветви C++ проходит сверка | — | `scripts/build-cpp-coverage.sh`, `docs/coverage/` |

**Полная проверка** — `scripts/verify-all.sh`: сборка, все unit-тесты, оракул и fuzz на версиях 13
и 16, дифференциальные прогоны. Около 12 минут на 16 ядрах (fuzz — основная часть).

Формат передачи начального стека в C++ (токены `fift`): целые числа; `N` (null); ячейки, срезы и
билдеры — как BOC в hex (`CB:`, `SB:`, `BB:`); кортежи — элементы и затем `TUP:<n>` (вложенность
рекурсивна); свой `c7` — токены кортежа и затем `SETC7`. NaN на стек не передаётся — его кладёт
пролог программы; числа шире 257 бит передать нельзя.

## 6. Что сделано

### 6.1. Хронология

**До 2026-10-19 (архив).** Порт контракта TON Storage на Tolk с дифференциальным тестированием;
затем доказательства о развёрнутом байткоде TON Storage на `tvm-lean`: 747 теорем, все пути
`recv_internal`, доказательство хэша кода. Вывод: доказательства о контракте не масштабируются и
бесполезны, пока модель не точна. Работа вынесена из модели в архив.

**Фаза 0 — чистая база.** Из накопленных изменений модели оставлены только относящиеся к модели:
исправления поведения версии 14, найденные сверкой; переписывание определений в тотальные (без
`partial`, вычислимые ядром Lean) с доказательствами равенства исходным (`TvmLean/Proofs/ModelEquiv.lean`);
обвязка сверки. Всё — тематическими коммитами в git.

**Фаза 1 — аудит по исходникам C++.**
- Опись всех 604 регистраций инструкций C++ (`docs/audit/cpp-registrations.csv`).
- Исчерпывающее сравнение декодеров: встроенные слова `fift` `(vmoplen)`/`(vmopdump)` обращаются
  прямо к таблице C++. Найдено 8724 расхождения, исправлено до 0: режим округления 3 в 13
  семействах деления (C++ декодирует и бросает `inv_opcode` уже при исполнении, после газа),
  `THROWANY` с аргументом 6, лишняя инструкция `EXTCALL` (в эталоне её нет).
- Кодировщик дополнен, добавлен кодировщик ячеек `encodeCp0Code` (биты, встроенные данные,
  ссылки). Проверка тождества на всех 2²⁴ значениях: модель декодирует ту же инструкцию с теми же
  аргументами, что и C++, кроме 7 групп равнозначных длинных форм (`XCHG s0` = `NOP` и т. п.,
  поведение и газ одинаковы).
- Опись 208 проверок глобальной версии в C++.

**Фаза 2 — измеримое «один в один» (идёт).**
- `fift` эталона собран с покрытием gcc без root; проходит весь оракул так же, как эталонный
  бинарник. Исходное покрытие строк `crypto/vm` — 43% (7519 из 17 469), ветвей — 32%.
- Найдено: **182 из 918 наборов тестов — пустые заглушки** (инструкции без единого теста); категория
  fuzz никогда не входила в полную сверку.
- Оракул расширен: кортежи в начальном стеке (`TUP:<n>`), свой `c7` (`SETC7`).
- Написаны генераторы и заполнены наборы: кортежи и null (34), окружение TON (60), исключения,
  `CDATASIZE`/`SDATASIZE`, `SETCP`, отладка (31), сообщения и действия (7). Осталась
  криптография (50).
- Fuzz включён в полную сверку; первый прогон нашёл два расхождения газа в словарях, исправлены.

### 6.2. Ошибки исходной модели, найденные и исправленные

| Инструкция | Ошибка | Основание в C++ |
|---|---|---|
| `QPOW2` | с версии 13 аргумент вне 0..1023 даёт NaN, модель бросала исключение | `exec_pow2` |
| семейства деления (`A90…A9D`, `B7A9x`) | режим округления 3 отвергался декодером; в C++ — декодируется, газ списывается, `inv_opcode` при исполнении | `OpcodeInstrFixed::dispatch`, `exec_divmod` и др. |
| `THROWANY` | аргумент 6 принимался; в C++ недопустим | `mkfixedrange(0xf2f0, 0xf2f6)` |
| `EXTCALL` | инструкции нет в эталоне | — |
| `TPUSH` | кортеж из 255 элементов: `type_chk`, модель давала `range_chk` | `pop_tuple_range` |
| `DICTSET` и др. | при исчерпании газа внутри инструкции модель списывала все созданные ячейки разом; C++ бросает на первом превышении | `register_cell_create` → `consume_gas` |
| `PFXDICTGET*` | на испорченном словаре модель не списывала загрузку узла, разбор которого упал | `PrefixDictionary::lookup_prefix` |
| `GETSTORAGEFEE` | цены хранения не срезом — в C++ это «цен нет», сбор 0 | `get_storage_prices` |
| `CHANGELIB` | глубина стека проверяется первой | `exec_change_lib` |
| поведение версии 14 | регистры управления, NaN в сдвигах, `SHRMOD`, слабые ключи ed25519, `ECRECOVER`, `ristretto255`, сбор в `SENDMSG`, `STSTDADDR` | см. `docs/model-changes.md` |

## 8. Открытые задачи — в порядке приоритета

1. **Криптография: 50 пустых наборов.** `BLS_*`, `CHKSIGNU/S`, `HASHEXT*`, `ECRECOVER`, `P256_*`,
   `RIST255_*` и др. Черновик для 8 хэш-инструкций — ветка `wip/crypto-oracle-draft` (раздел 11,
   не собран и не проверен). Для подписей и кривых нужны корректные тестовые векторы.
2. **Непроверенные списания газа.** 65 мест (`st.consumeGas` без немедленной проверки лимита): 34
   в `Exec/Crypto/Ext.lean`, 9 в механизме шага и `RUNVM`, остальные по одному-два в инструкциях
   (`SENDRAWMSG`, `SETCODE`, `RAWRESERVE*`, `ROLL`/`REVERSE`, `ENDC`, `STBREF*`, `HASHEXT`,
   `DICTGETNEAR` и др.). Расхождение с C++ возможно, только если после такого списания в той же
   инструкции есть ещё списания — прецедент `DICTSET`. Нужен разбор каждого места по C++ и тесты
   с исчерпанием газа внутри инструкции (`SETGASLIMIT` перед ней).
3. **Покрытие.** Ограничить область измерения кодом исполнения (исключить `db/`,
   `large-boc-serializer.cpp`, `utils.cpp`, `memo.*`), мерить ветви, прогнать через сборку с
   покрытием все категории, включая fuzz; на каждую непокрытую ветвь — целевой тест оракула.
4. **Версии ниже 13.** 87 проверок с порогом ≤ 12 и ограничения `require_version` у 89 инструкций.
   Оракул уже умеет любую версию (`TVMLEAN_GLOBAL_VERSION`).
5. **Криптография на Lean.** Сейчас ed25519, secp256k1, P-256, ristretto255, BLS12-381, blake2b,
   keccak — внешние функции на C (`c/`, `TvmLean/Native/`). SHA-256/512 уже на Lean. Цель — модель
   без внешних функций.
6. **Фазы транзакции** по `crypto/block/transaction.cpp`: хранение, кредит, действия, bounce. Сейчас
   есть только фаза исполнения (`TvmLean/Semantics/Contract.lean`).
7. **Доказательства о модели.** Недоказанные равенства переписанных определений исходным
   (`takeRefsInv` в декодере, цикл `HASHEXT`, `intToBigInt52Digits`, неподвижные точки `Cell.beq`
   и `computeLevelInfo?`) — `docs/model-changes.md`.
8. **Корпус дифференциальных прогонов** — сейчас только TON Storage; нужны другие реальные контракты.
9. Мелочи: генератор `DICTIADDB` иногда строит неверный ключ и печатает `PANIC` (дефект данных
   теста); 7 канонических форм кодировщика (косметика).
10. Затем — стадия II: индукция, символьное исполнение, инварианты.

План по фазам с критериями готовности — `docs/project/roadmap.md`.

## 10. Правила работы и подводные камни

**Правила.**
1. Любое изменение модели обосновано строкой C++ на `3d478cb`.
2. На каждое исправление — случай оракула, воспроизводящий расхождение.
3. Прежде чем считать работу готовой — полная проверка, **включая fuzz**.
4. Один коммит — одна тема; в сообщении — что, почему, ссылка на C++.
5. В модели нет `partial`, `sorry`, `admit`; рефакторинг — с доказательством равенства исходному.
6. **Одна рабочая сессия на одну рабочую копию** (раздел 11).

**Подводные камни.**
- У индуктивного типа в рантайме Lean ограничено число конструкторов; у `Instr` их 244, новый не
  добавить — новые конструкторы кладутся во вложенные типы (`ArithExtInstr` и т. п.).
- `set_option … in` ставится **перед** doc-комментарием.
- `fift`: `(vmoplen)` — `( s cp -- len )`, где `len = ссылки·65536 + биты`, 0 — недопустимый
  опкод; `(vmopdump)` — `( s cp -- s' str )`.
- Газ в C++ проверяется **при каждом** `consume_gas`; модель должна списывать в том же порядке
  через проверяющие `VM.consumeGas`, `VM.registerCellLoad`, `VM.chargeCellCreates`.
- Счётчики `gcov` пишутся только при нормальном завершении процесса.
- `panic!` в тестах Lean печатает сообщение и продолжает работу.
- На сервере `tail` — реализация uutils: только `tail -n N`.
- Сборка C++ с покрытием: старый gnulib не собирается как C23 под gcc 15 — `-std=gnu17` (в скрипте).
