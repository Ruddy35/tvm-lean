# Передача проекта: формальная модель TVM на Lean 4

Документ для разработчика, который продолжает работу. Он построен по уровням: каждый следующий
раздел углубляет предыдущий. Прочитав разделы 1–4, вы понимаете, что это и зачем. Прочитав всё —
можете работать.

Дата передачи: 2026-10-19, обновлён 2026-10-20 после третьей сессии (покрытие ветвей C++,
глобальные версии 0..16, криптография на Lean, начало фаз транзакции). Ветка: `formal-tvm`, коммит
последней полной проверки — `0866014` (поверх него только документы и скрипты серверов); работа после него — в
`claude/bold-turing-6i3ctb`, проверена локально и ждёт полной проверки на сервере (раздел 7).

## 1. За две минуты

- **Что это.** Модель виртуальной машины блокчейна TON (TVM) на языке Lean 4 — исполняемая
  спецификация, которая должна вести себя **ровно так же**, как C++-реализация TVM.
- **Зачем.** Чтобы на её основе формально доказывать свойства любого смарт-контракта TON по его
  байткоду: «инвариант I сохраняется при любой транзакции». Модель — фундамент; если она хоть в
  чём-то расходится с C++, доказательства о ней ничего не говорят о настоящей сети.
- **Основа не наша.** Мы взяли открытый проект `Gusarich/tvm-lean` и дорабатываем его в своей
  ветке. Он **не является истиной**: в нём находились и исправлены ошибки. Истина — C++-код TON
  конкретного коммита.
- **Как проверяем «один в один».** Каждое поведение модели сравнивается с C++ на одних и тех же
  входах: случаи оракула (C++ запускается через `fift`), случайные (fuzz) случаи, исчерпывающая
  проверка декодера на всех 2²⁴ опкодах, повторы реальных прогонов контракта. Сейчас всё проходит.
- **Где мы.** Декодер инструкций доказанно совпадает с C++ на всём пространстве опкодов. У всех
  инструкций есть тесты против C++, каждый набор исполняет именно свою инструкцию, и всё сверяется
  на **каждой глобальной версии 0..16**; найдено и исправлено более 40 ошибок исходной модели; все
  списания газа сверены с порядком C++; непокрытые ветви C++ разобраны по всем файлам кода
  исполнения. Криптография переписана на Lean — модель не вызывает внешних функций. Фаза 5 закрыта:
  транзакция целиком (`crypto/block/transaction.cpp`), обычная и tick-tock, сверяется с эмулятором
  транзакций C++ на всех версиях (40 125 случаев, все контракты `crypto/smartcont/auto`). Впереди —
  фаза 6 (доказательства о самой модели) и только потом доказательства о контрактах.

## 2. Цель проекта

Конечная цель — **проверять смарт-контракты TON формально, по байткоду, методом индукции**:

1. Начальное состояние контракта удовлетворяет инварианту.
2. Любая транзакция, переводящая состояние, удовлетворяющее инварианту, сохраняет его.
3. Значит, инвариант верен всегда.

Для этого нужна модель TVM, о которой можно доказывать (Lean 4) и которая совпадает с настоящей
машиной во всём, что наблюдаемо: результат, исключение, код выхода, **израсходованный газ** (это
деньги), состояние `c4` (данные контракта) и `c5` (исходящие действия).

Работа разбита на две стадии, строго по порядку:

| Стадия | Содержание | Состояние |
|---|---|---|
| I. Полная модель | всё, что исполняется при обработке транзакции, на Lean, совпадает с C++ | идёт |
| II. Индукция и инварианты | общая теорема индукции по транзакциям, символьное исполнение байткода с доказанной корректностью, сведение проверки контракта к условиям для решателей | не начата |

Важное решение, принятое по ходу: сначала мы доказывали свойства конкретного контракта (TON
Storage) прямо на модели — получилось 747 теорем, — но это не масштабируется и опирается на модель,
в которой потом нашлись ошибки. Поэтому работа над контрактами отложена (архив, см. раздел 9), а
все силы — на полноту и точность модели.

## 3. Источник истины: C++ и глобальные версии

### 3.1. Эталон

**Истина — исходный код C++ репозитория `ton-blockchain/ton` на коммите
`3d478cbde854be03a18ab2a59f8fc3c565cf7d14`** (2026-08-17, релиз v2026.08). Ровно из этого
коммита собран `fift`, которым пользуется оракул (`fift -V` печатает этот хэш). Все обоснования
изменений модели ссылаются на код этого коммита: файл, функция, строка.

Основные места в C++:

| Что | Где |
|---|---|
| Исполнение инструкций | `crypto/vm/*ops.cpp` (`arithops`, `cellops`, `contops`, `dictops`, `stackops`, `tonops`, `tupleops`, `debugops`) |
| Таблица декодирования, газ за инструкцию | `crypto/vm/opctable.cpp` (`OpcodeInstr*::dispatch`), `cp0.cpp` |
| Цикл VM, исключения, газ | `crypto/vm/vm.cpp`, `vm.h` |
| Словари | `crypto/vm/dict.cpp` |
| Ячейки, срезы | `crypto/vm/cells/` |
| Фазы транзакции | `crypto/block/transaction.cpp` |

Правило: **если модель, тест или документация расходятся с C++, прав C++.** Это касается и тестов
исходного проекта — некоторые из них закрепляли неверное поведение (раздел 6.3).

### 3.2. Глобальные версии

Сеть TON имеет **глобальную версию** (параметр конфигурации 8, в C++ — `VmState::global_version`).
Одна и та же программа ведёт себя по-разному в разных версиях:

- **инструкции появляются с какой-то версии**: `->require_version(N)` в регистрации C++ (89
  инструкций, версии 4–12). Ниже своей версии инструкция — недопустимый опкод;
- **поведение инструкций меняется**: проверки `get_global_version() >= N` в коде исполнения
  (например, с версии 13 `QPOW2` вне диапазона даёт NaN вместо исключения; с версии 14 повторная
  установка регистра управления — тихая пустая операция);
- **фазы транзакции** тоже зависят от версии (`transaction.cpp`).

Опись всех 208 проверок версии в C++ — `docs/audit/cpp-global-version.csv`, разбор —
`docs/audit/README.md`, раздел 3.

**Модель поддерживает все версии 0..16** (`VmState.globalVersion`, по умолчанию 13): все проверки
уровня VM из описи есть в модели (фаза 3, `docs/model-changes.md`, раздел 1.3), опкоды более поздней
версии — недопустимые (`Model/Instr/Codepage/Versions.lean`). Полная сверка с C++ идёт на **каждой
версии 0..16** (16 — `SUPPORTED_VERSION` эталонного релиза). Пороги в коде VM: 4, 5, 6, 9, 10, 11,
12, 13, 14; версии 0–3, 6–8 и 14–16 ведут себя одинаково внутри группы.

проекта — `docs/model-changes.md`; история — `git log e1f334f..formal-tvm`.

## 5. Как устроена проверка «один в один»

Модель запускается рядом с C++ на одинаковых входах, сравнивается всё наблюдаемое.

| Вид проверки | Что сравнивает | Объём | Где |
|---|---|---|---|
| Unit-тесты | поведение модели с ожиданиями, записанными в тесте (без C++); у криптографии — с векторами независимых реализаций | 5990 | `Tests/Instr/*/*.lean`, поле `unit` |
| **Оракул** | модель и C++ (`fift runvmx`) на заданных программе, стеке, `c7`: код выхода, газ, весь стек, хэши `c4`/`c5` | 48 618 случаев × 17 версий | поле `oracle` и генераторы `Tests/Harness/Gen/*`; `Tests/Harness/OracleHarness.lean`, `oracle/fif/` |
| **Fuzz** | то же, на случайных входах из генераторов наборов | 417 516 случаев × 17 версий | поле `fuzz`; `Tests/Harness/FuzzHarness.lean` |
| Дифференциальные прогоны | модель против записанных прогонов C++ реального контракта (TON Storage) | 35 889 | `TvmLean/Validation/Diff/`, `~/ws/fixtures` |
| Аудит декодера | длина и допустимость каждого 24-битного опкода (2²⁴ × 2 хвоста) против таблицы C++; тождество инструкции через пересборку | 33,5 млн | `tools/audit/decoder/` |
| Покрытие C++ | какие строки и ветви C++ проходит сверка | — | `scripts/build-cpp-coverage.sh`, `docs/coverage/` |
| **Транзакции** | модель и эмулятор транзакций C++ (`libemulator.so` эталона) на одних конфигурации, `ShardAccount`, входящем сообщении, времени и зерне: хэши ячеек транзакции и нового счёта, либо отказ внешнего сообщения | 40 125 случаев на версиях 0..16 + 3000 fuzz | `TvmLean/Transaction/`, `Tests/Tx/`, `tools/txoracle/`, `tvm-lean-tx-test` |

**Полная проверка** — `scripts/verify-all.sh`: сборка, все unit-тесты, оракул и fuzz на каждой
версии 0..16 (`VERSIONS`, не больше `PAR` заданий сразу), дифференциальные прогоны, транзакции на
всех версиях и их fuzz (`TX_FUZZ`, по умолчанию 3000). Итог — строка `verify: OK` или
`verify: FAILED (<задания>)` и такой же код выхода; упавшие задания отмечаются в `$OUT/failed/`.

Формат передачи начального стека в C++ (токены `fift`): целые числа; `N` (null); ячейки, срезы и
билдеры — как BOC в hex (`CB:`, `SB:`, `BB:`); кортежи — элементы и затем `TUP:<n>` (вложенность
рекурсивна; `tuple` в `fift` берёт не больше 255 элементов, дальше — каждый элемент и `TPUSH`);
свой `c7` — токены кортежа и затем `SETC7`. NaN на стек не передаётся — его кладёт пролог
программы; числа шире 257 бит передать нельзя.

## 6. Что сделано

### 6.1. Хронология

**До 2026-10-19 (архив).** Порт контракта TON Storage на Tolk с дифференциальным тестированием;
затем доказательства о развёрнутом байткоде TON Storage на `tvm-lean`: 747 теорем, все пути
`recv_internal`, доказательство хэша кода. Вывод: доказательства о контракте не масштабируются и
бесполезны, пока модель не точна. Работа вынесена из модели в архив.

**Фаза 0 — чистая база.** Из накопленных изменений модели оставлены только относящиеся к модели:
исправления поведения версии 14, найденные сверкой; переписывание определений в тотальные (без
`partial`, вычислимые ядром Lean) с доказательствами равенства исходным (`TvmLean/Proofs/ModelEquiv.lean`);
обвязка сверки. Всё — тематическими коммитами в git.

**Фаза 1 — аудит по исходникам C++.**
- Опись всех 604 регистраций инструкций C++ (`docs/audit/cpp-registrations.csv`).
- Исчерпывающее сравнение декодеров: встроенные слова `fift` `(vmoplen)`/`(vmopdump)` обращаются
  прямо к таблице C++. Найдено 8724 расхождения, исправлено до 0: режим округления 3 в 13
  семействах деления (C++ декодирует и бросает `inv_opcode` уже при исполнении, после газа),
  `THROWANY` с аргументом 6, лишняя инструкция `EXTCALL` (в эталоне её нет).
- Кодировщик дополнен, добавлен кодировщик ячеек `encodeCp0Code` (биты, встроенные данные,
  ссылки). Проверка тождества на всех 2²⁴ значениях: модель декодирует ту же инструкцию с теми же
  аргументами, что и C++, кроме 7 групп равнозначных длинных форм (`XCHG s0` = `NOP` и т. п.,
  поведение и газ одинаковы).
- Опись 208 проверок глобальной версии в C++.

**Фаза 2 — измеримое «один в один» (идёт).**
- `fift` эталона собран с покрытием gcc без root; проходит весь оракул так же, как эталонный
  бинарник. Исходное покрытие строк `crypto/vm` — 43% (7519 из 17 469), ветвей — 32%.
- Найдено: **182 из 918 наборов тестов — пустые заглушки** (инструкции без единого теста); категория
  fuzz никогда не входила в полную сверку.
- Оракул расширен: кортежи в начальном стеке (`TUP:<n>`), свой `c7` (`SETC7`).
- Написаны генераторы и заполнены наборы: кортежи и null (34), окружение TON (60), исключения,
  `CDATASIZE`/`SDATASIZE`, `SETCP`, отладка (31), сообщения и действия (7). Осталась
  криптография (50).
- Fuzz включён в полную сверку; первый прогон нашёл два расхождения газа в словарях, исправлены.

**Фаза 2, вторая сессия: криптография и газ.**
- Нативная криптография модели на Linux линкуется с теми же библиотеками (sodium, OpenSSL,
  secp256k1, blst), что и C++, из Release-сборки эталона (`TVMLEAN_TON_BUILD`, раздел 9).
- Черновик `wip/crypto-oracle-draft` доведён; закрыты все 50 криптографических наборов. Векторы — из
  независимых реализаций на Python (`tools/crypto/`: ed25519 по RFC 8032, ECDSA secp256k1 и P-256,
  ristretto255 по RFC 9496, BLS12-381 через `py_ecc` с тем же DST, что C++); 22 набора сверены с
  ними и unit-тестами. Добавлен отсутствовавший набор `GETEXTRABALANCE`.
- Ed25519 переписан на Lean по OpenSSL (`TvmLean/Model/Crypto/Ed25519.lean`): C++ проверяет подпись
  через OpenSSL, а модель — через libsodium, у которой другие правила для точек малого порядка.
- Пройдены все 65 непроверенных списаний газа (`docs/audit/gas-charges.md`): 7 наблюдаемых
  расхождений исправлены, остальные доказанно ненаблюдаемы.

**Фаза 2, третья сессия (2026-10-20): покрытие ветвей C++.**
- Область измерения — код исполнения (`SCOPE=exec`), метрика — ветви. Прогон с покрытием: весь
  оракул и fuzz на версиях 13 и 16 (`scripts/cpp-coverage-run.sh`); непокрытые ветви с исходными
  строками — `tools/coverage/uncovered.py`.
- По непокрытым ветвям написаны целевые случаи оракула; найдено и исправлено (раздел 6.2): фиксация
  `c4`/`c5` (глубина 512 включительно, уровень 0), `SENDMSG` (цены и ограничения размера, подсчёт
  ячеек, проверка сообщения как в TL-B, рабочие цепочки, сообщение-библиотека), 17 инструкций без
  ранней проверки глубины стека, загрузка ячеек-библиотек во всех инструкциях и словарях,
  исполнение экзотической ячейки как кода в `IF*REF`, ограничение глубины новой ячейки 1024.
- Каждый набор теперь прогоняется и на коротких стеках (0..5 значений): так найдены 17 инструкций
  без ранней проверки глубины.
- Проверка `--opcode-check`: 27 наборов не исполняли свою инструкцию — проверяли соседнюю
  (`PUSHINT n; PLDIX` вместо `PLDI n` и т. п.), потому что когда-то ассемблер не умел их форму;
  добавлены случаи с настоящими опкодами, проверка входит в `verify-all.sh`.
- Второй проход (продолжения, `RUNVM`, словари): наборы циклов передавали условием и телом
  `quit`-продолжения, поэтому продолжения циклов не исполнялись ни разу (`WhileCont` в C++ — 0
  вызовов). Случаи с настоящими циклами (`Tests.Gen.Loops`) нашли: сброс `c0` в конце `*END`-циклов,
  пропуск проверки `nargs` при прыжке (циклы, `TRY`, `IFNOTJMP`), газ длинных цепочек прыжков
  (`free_nested_cont_jump`), `BOOLEVAL` (`PushIntCont`). `RUNVM`: дочерняя VM не могла запустить
  `RUNVM` и останавливалась через 50 000 шагов. Словари: узлы, загруженные до ошибки, списывались
  неточно (префиксные словари, удаление со слиянием ребра). Шаг VM, дочерней VM и трассировки —
  теперь одна функция (`Step/Core.lean`): было три копии.
- Недостижимые из исполнения ветви разобраны в `docs/coverage/README.md`.
- Проход по коротким стекам теперь берёт за основу случай, исполняющий собственный опкод набора
  (44 набора брали соседнюю инструкцию, 36 не проходили вовсе): нашёл `BLKSWX` и `REVX` без
  `check_underflow(2)`.

**Фаза 3 (2026-10-20): глобальные версии 0..16.** Модель повторяла версию 13 на всех версиях; по
описи `docs/audit/cpp-global-version.csv` закрыты все ветви кода VM по версии (раздел 6.2,
`docs/model-changes.md`, раздел 1.3): опкоды поздних версий; формы `ADD` деления (с 4); цепочки
`jump_to` без `adjust_jump_cont` (до 9); счётчики стековых операций до 255 (до 4); газ без
немедленной проверки, `CHKSIGN` без счёта (до 4); NaN через `BigInt` C++ в сдвигах, `AND`, `OR`,
`MULRSHIFT`, `LSHIFTDIV` (до 13); режимы `RAWRESERVE`, `SETLIBCODE`, `CHANGELIB` (до 4); `XLOAD` (до 5);
`HASHEXT` (до 9); `PFXDICT*` (до 9); anycast и `addr_var` (до 10); `GLOBALID` (до 6); `SENDMSG` (до 6,

**Фаза 4 (2026-10-20): криптография на Lean.** Все внешние функции криптографии заменены
определениями на Lean (`TvmLean/Model/Crypto/`, `docs/model-changes.md`, раздел 1.4), каждое — по коду
той библиотеки, которую вызывает C++ эталона: Keccak и BLAKE2b (`HASHEXT`); secp256k1 по libsecp256k1

бесконечности, ключ с чётным `y`, твик меньше `n`); P-256 по OpenSSL (`P256_CHKSIGNU/S`); ristretto255
по libsodium (`RIST255_*`, включая запись результата перед ошибкой в `mul_base`); BLS12-381 по blst
(`BLS_*`: умножения GLV/GLS, таблицы мультиэкспоненты, бесконечность в спаривании, проверки подгруппы
только там, где их делает blst). Каждая реализация сверена с самой библиотекой C++ на тысячах случаев;
fuzz получил генераторы всех семейств (`Tests.Gen.Crypto.fuzzFor`). Объект `Host`, файлы `c/` и
нативная сборка удалены: модель — чистый Lean, библиотеки эталона для сборки не нужны.

**Фаза 5 (идёт, с 2026-10-20): транзакция.** Оракул — эмулятор транзакций эталона (`libemulator.so`,

   примитивы построителя сохраняют их при проверках, которые делают инструкции (`canExtendBy`);
   ячейка, у которой вычисляется информация об уровнях (всякая ячейка с хэшем), корректна;
   `TvmLean/Proofs/WF/` — корректность всего состояния VM (`VmState.WF`): шаг и прогон VM её
   сохраняют для всех инструкций без условий (`VmState.WF.step'`, `run'`, `WF/All.lean`; критерий
   фазы 6 выполнен); как доказывается семейство — docstring `TvmLean/Proofs/WF/Step.lean` и
   `TvmLean/Proofs/WF/JoinPoints.lean`.
   Криптография на Lean сверена с библиотеками C++
   на случаях, но не доказана (например, что `Weierstrass.add` — групповой закон).
6. **Корпус дифференциальных прогонов** — сейчас только TON Storage; нужны другие реальные
   контракты. Фикстуры есть только на сервере (`~/ws/fixtures`), в репозитории их нет. Контракт
   хранения TON Storage сверяется и транзакциями с эмулятором (`Tests/Tx/StorageContract.lean`:
   случаи строятся из репозитория, ответы C++ считаются при каждом прогоне).
7. Мелочи: 7 канонических форм кодировщика (косметика); поле `savedC0` обычного продолжения не
   читается — удалить; топливо (число шагов) главной VM в сверке задаётся вручную (1 000 000), как у
   дочерних VM его можно выводить из газа (`GasLimits.stepBound`; модель транзакции так уже делает).
   Наборы, где своя инструкция исполняется лишь в части случаев: `--opcode-share` печатает наборы,
   в которых своя инструкция есть в коде меньше чем половины случаев оракула, и сколько случаев всех
   наборов её исполняют (`--filter S` — случаи набора `S` без неё). На 2026-10-20 таких наборов 35
   (в основном словарные наборы-семейства: `DICTUSETB` проверяет и `DICTSETB`, и `DICTISETB`); в
   каждом опкоде из них — не меньше 20 случаев оракула по всем наборам, меньше всего у `STREF_ALT`,
   `STSLICE_ALT` (20; `exec_*` общий с `STREF`, `STSLICE`), `DICTIMIN` (23), `PUSHSLICE` (24). Усилить
   при случае — так же, как в `Tests.Gen.OwnOpcode`.
8. **Стадия II — индукция, символьное исполнение, инварианты (идёт).** Принцип индукции по
   транзакциям доказан (`TvmLean/Proofs/Tx/`, `d455128`..`d919cbb`): `Reachable.good` — инвариант
   `Inv` кода и данных выполняется у каждого активного счёта всякой шард-записи, достижимой
   транзакциями (`emulate` и `emulateTickTock`, любые сообщения, время, библиотеки) из начальных,
   если он верен в начале, у развёртываемых `StateInit` и сохраняется каждым зафиксированным прогоном
   VM фазы исполнения (`RunPreserves`: `Ran code data c4 c5` — прогон от любого `VmStart`, новый код —
   старый или цель `SETCODE` из `c5`). Формы для доказательств о контракте: `good_split`,
   `code_fixed` («код не меняется»), `spec`. Всё остальное (фазы хранения, кредита, отскока, откат,
   фаза действий, развёртывание, запись счёта и чтение обратно) доказано один раз. Ограничения:
   шаг — любая транзакция, которую возвращает модель (`Step.of_emulate`, `76d479c`: `Fits` выведено из
   модели); инвариант — только о коде и данных; `Init` (какие `StateInit` развёртываются) —
   параметр, потому что у хэша ячейки не один прообраз. Доказательство чтения счёта нашло
   расхождение с C++, исправлено (`702751f`, случаи `cov/state/`): C++ `compute_state`
   (transaction.cpp:3552-3735) проваливает транзакцию, когда поле нового счёта не помещается (баланс
   или долг ≥ 2¹²⁰, статистика хранения ≥ 2⁴⁸, в том числе перенос при вычитании битов в 64-битной
   арифметике), модель обрезала. То же расхождение в `Tx.serialize` (поля описания транзакции:
   сборы фазы хранения, газ, `total_fees`) — исправляется (помощник). Модуль `ActionPhase`
   собирается ~2 мин и 3,4 ГБ (`ulimit -v` не меньше 9 ГБ).
   Символьное исполнение: `vm_run` проходит весь `recv_external` wallet v3 от `computePhaseInit`
   (`TvmLean/Proofs/Exec/Pilot/Wallet3.lean`, ~6 мин сборки); 287 спецификаций инструкций
   (`TvmLean/Proofs/Exec/Spec/`), правило цикла (`VmState.runWith_loop`), поиск в символьном словаре
   (`Dict.get`). Дальше: прогоны VM конкретного кода (`Ran`) закрывать символьным исполнением и
   связать с `ContractSpec` (`TvmLean/Proofs/Contracts/Spec.lean`); wallet v3 от байткода до
   теоремы индукции сделан (`Contracts/Wallet3Induction.lean`: код, ключ и подкошелёк не меняются
   никогда; прогоны — `Contracts/Wallet3Run/`, до версии 4 и с неё отдельно: с версии 4 нехватка газа
   останавливает VM сразу, vm.h:203-209), доказательство прогонов там написано под контракт.
   Общее средство сделано: `tools/contract-check` (раздел в `tools/README.md`) по байткоду и файлу
   инварианта строит модуль Lean с теоремой по `Reachable.code_fixed` и доказывает её тактикой
   `ran_preserves` (`TvmLean/Proofs/Check/Tactic.lean`: шесть видов старта — внешнее, внутреннее,
   tick-tock, версии до 4 и с 4; каждый путь до конца, длинные пути режутся на вспомогательные
   теоремы), иначе печатает пути, где инвариант не показан. Доказаны так wallet v3, wallet v2, simple
   wallet (`TvmLean/Proofs/Check/Contracts/`); ложный инвариант даёт путь. Пока не умеет: перебор
   неизвестного словаря (`DICTIGETNEXT`), словари в данных, вызовы с аргументами, чтение параметров
   конфигурации, `SETCODE` (только инварианты при неизменном коде), действия кроме `SENDRAWMSG` и
   `RAWRESERVE`; контракт с процедурами через `CALLDICT` пока не укладывается во время. Дальше —
   эти пункты, затем TON Storage средством. TON Storage доказан напрямую (`5fb753f`,
   `Contracts/StorageInduction.lean`: код и неизменяемые поля не меняются, активный остаётся
   активным; прогоны `Contracts/StorageRun/`, приёмы — ячейки, которых прогон не знает
   `Exec/Framed*.lean`, короткий путь исключения, обобщение газа и значений, разрезы прогона); его
   транзакции сверяются (`Tests/Tx/StorageContract.lean`). Модуль `StorageRun/Close` собирается
   ~25 мин и ~10 ГБ: библиотеку доказательств целиком собирать на серверах, не локально. Правило: имя объявляется в библиотеке доказательств один раз (общее — в
   `TvmLean/Proofs/Basic.lean`); `TvmLean/Proofs/All.lean` импортирует все корни `TvmLeanProofs` —
   новый корень добавлять и туда. Локальная машина (15 ГБ, 4 ядра): параллельные сборки Lean дважды
   роняли контейнер по памяти (модуль доказательств — до 3,4 ГБ резидентно, `lake` собирает
   несколько сразу); каждую сборку запускать в своей группе памяти с ограничением (cgroup v1:
   `memory.limit_in_bytes` в подгруппе своей группы из `/proc/self/cgroup`), сумма ограничений
   одновременных сборок — не больше ~13 ГБ, `LEAN_NUM_THREADS=2`.


## 10. Правила работы и подводные камни

**Правила.**
1. Любое изменение модели обосновано строкой C++ на `3d478cb`.
2. На каждое исправление — случай оракула, воспроизводящий расхождение.
3. Прежде чем считать работу готовой — полная проверка, **включая fuzz**.
4. Один коммит — одна тема; в сообщении — что, почему, ссылка на C++, чем проверено.
5. В модели нет `partial`, `sorry`, `admit`; рефакторинг — с доказательством равенства исходному.
6. **Одна рабочая сессия на одну рабочую копию** (раздел 11).

**Подводные камни.**
- У индуктивного типа в рантайме Lean ограничено число конструкторов; у `Instr` их 244, новый не
  добавить — новые конструкторы кладутся во вложенные типы (`ArithExtInstr` и т. п.).
- `set_option … in` ставится **перед** doc-комментарием.
- `fift`: `(vmoplen)` — `( s cp -- len )`, где `len = ссылки·65536 + биты`, 0 — недопустимый
  опкод; `(vmopdump)` — `( s cp -- s' str )`.
- Газ в C++ проверяется **при каждом** `consume_gas`; модель должна списывать в том же порядке
  через проверяющие `VM.consumeGas`, `VM.registerCellLoad`, `VM.chargeCellCreates`.
- Счётчики `gcov` пишутся только при нормальном завершении процесса.
- `panic!` в тестах Lean печатает сообщение и продолжает работу.
- На сервере `tail` — реализация uutils: только `tail -n N`.
- Сборка C++ с покрытием: старый gnulib не собирается как C23 под gcc 15 — `-std=gnu17` (в скрипте).
- `assembleCp0` кодирует только биты: инструкции со ссылками (`PUSHREF`, `PUSHCONT` со ссылками,
  `IF*REF`) им не собираются (`invOpcode`). Код со ссылками собирает `encodeCp0Code`
  (`Tests.Gen.Control`, `Tests.Tx.Gen.asm?`). Генератор транзакций до `asm?` молча подставлял пустую
  ячейку: случаи фазы действий с отправками, `SETCODE`, `c5` и случайные транзакции с действиями
  исполняли пустой код у обеих сторон и совпадали. Теперь `tvm-lean-tx-test` не запускается, если
  контракт не собирается или случай не сериализуется.
- BOC от эмулятора C++ содержит CRC, BOC модели — нет: транзакции сравниваются по хэшам ячеек.
- В модели транзакции поля C++ `msg_state_used` и `account_activated` всегда ложны: C++ их не
  устанавливает на этом пути.
- Проверка газа внутри инструкции: `PUSHINT lim; SETGASLIMIT; <инструкция>`, перебор `lim` с шагом 1
  вокруг цены; газ кода пролога считать декодером (`decodeCp0WithBits` + `instrGas`), длинный
  `PUSHINT` (0x82) стоит 13 бит, а не по длине.
