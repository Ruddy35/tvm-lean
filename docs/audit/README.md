## 2. Исчерпывающее сравнение декодеров — выполнено

`tools/audit/decoder/run.sh` (`Apps/AuditDecoder.lean` и `tools/audit/decoder/cpp.fif`): каждое
24-битное значение с двумя хвостами (480 нулей или единиц) и четырьмя пустыми ссылками декодируется
моделью и таблицей диспетчеризации C++ (`(vmoplen)`, `(vmopdump)`). Дополнительно для каждого
16-битного префикса модель пересобирает декодированную инструкцию (`encodeCp0`), а C++ печатает и
исходный опкод, и пересборку: совпадение означает ту же инструкцию с теми же аргументами.

| Показатель | До исправления | После |
|---|---|---|
| Значений (на каждый хвост) | 16 777 216 | 16 777 216 |
| Допустимых: C++ / модель | 15 313 543 / 15 305 843 | 15 313 543 / 15 313 543 |
| Расхождений длины или допустимости | 8724 | **0** |
| Пересборка: проверено | 59 794 | 59 826 |
| Пересборка: инструкция по C++ различается | 7 | 7 |
| Пересборка: кодировщик модели не умеет | 6371 | 6371 → 5920 → **0** (`encodeCp0Code`) |

Исправлено (коммит «model: decoder mirrors the C++ dispatch table exactly»):

- семейства деления (`A90…A9D`, тихие `B7A9x`): режим округления 3 декодируется, как в C++, и
  выполняется как `inv_opcode` после списания газа инструкции;
- `F2F6` недопустим (`mkfixedrange(0xf2f0, 0xf2f6)`);
- `EXTCALL` удалён — такой инструкции в эталоне нет.

Остаётся:

- 7 расхождений пересборки — длинные формы с нулевым или малым аргументом (`XCHG s0` = `11 00`,
  `PUSH s0`, `POP s0`, `GETPARAMLONG 0` и т. п.): модель декодирует их правильно, а при пересборке
  выбирает короткую каноническую форму. Это свойство кодировщика, не декодера.
- Пересборка теперь покрывает всё: кодировщик `encodeCp0Code` выдаёт биты, встроенные данные и
  ссылки. Для всех 59 826 декодированных инструкций (на каждый хвост) запись C++ пересборки совпадает
  с исходной, кроме 7 канонических форм выше. Значит, для каждого 16-битного префикса модель
  декодирует ту же инструкцию с теми же аргументами, встроенными данными и ссылками, что и C++.
- Тождество на всех 2²⁴ значениях (`tools/audit/decoder/identity_all.sh`): для каждого из
  15 313 543 значений, которые C++ декодирует (на каждый хвост), C++ печатает пересборку модели так же,
  как исходный код, кроме тех же 7 групп длинных форм (1539 значений: `XCHG s0`/`s1`, `PUSH s0`/`s1`,
  `POP s0`/`s1` с любым третьим байтом, `GETPARAMLONG 0..2`). В них модель декодирует инструкцию с
  тем же поведением (`XCHG s0` — пустая операция, `PUSH s0` = `DUP`, …) и той же длиной, то есть
  тем же газом. Итог: декодер модели читает ту же инструкцию с теми же аргументами, что и C++, на
  всём пространстве опкодов.
- Запись инструкций различается в 28 158 случаях из 59 826: модель печатает не в формате C++. На
  семантику не влияет; проверка тождества идёт через пересборку.
- Газ и поведение `invalidArgs` подтверждены оракулом: 17 случаев в наборе `DIV`, все 13 семейств
  и обрезанный опкод, версии 13 и 16.

## 4. Покрытие символьным исполнением — опись готова

которыми он пересоздаётся): что из набора инструкций и шаблонов управления исполняют `vm_run`
(`TvmLean/Proofs/Exec/Tactic.lean`) и `ran_case` (`TvmLean/Proofs/Check/Tactic.lean`) в окружении
модуля `tools/contract-check`, то есть то, что получает доказательство.

- **Формы инструкций.** 919 форм таблицы декодирования, каждая перебрана по аргументам (32 473
  опкода), декодирована декодером модели и классифицирована: лемма `vm_spec`, которая к ней подходит
  (как её ищет `applySpec`), иначе обработчик модели — статически (какие программы VM он исполняет:
  считаются леммой `vm_run`, разворачиваются `unfoldModelRun` или блокируют) и прогоном на символьном
  состоянии фазы исполнения со стеком её сигнатуры. Сейчас (после волны 0, `5d8374b`): **425
  покрыты леммами** (326 — всегда, 99 — с условием), **306 исполняются развёрткой обработчика**,

- **Предпроверка** (`contract-check <код> --precheck`): весь код контракта, достижимый из корня,
  дизассемблирован и классифицирован до начала доказательства; прогнана на 26 кодах

  (`LDDICT`/`STDICT`, перебор), `PUSHCTR`/`POPCTR`, конфигурация; у новых кодов — те же (`STDICT`,

- **`contract-check` на контрактах корпуса** (`tools/contract-check/examples/`: `wallet4`,

  — индекс и коллекция не меняются): **NOT PROVED**. Внутреннее сообщение у всех останавливается на

  ячейку `msg`; предпроверка этого не видит (у `CTOS` лемма есть). Внешние сообщения v4r2 и v5r1
  доходят до `COMMIT` после `set_data` и дальше не идут (шаблон `COMMIT` выше); для этого кошелькам
  нужны леммы о срезах однобитового поля `#[b]` (в файлах инвариантов), без них ключ читается как
  `bitsToNat (natToBits key 256 ++ #[b].extract 0 0)` и прогон останавливается на `CHKSIGNU`.
  Внешние сообщения кошелька жетонов и элемента NFT и tick-tock доказаны (у v5r1 tick-tock — с

не решено — `if` на `k ≤ gv`), опкод версии выше — недопустимый опкод, как в C++; `unfoldModelRun`
разворачивает `private`-определения модулей модели (`IFBITJMP*`, `PFXDICT*` теперь развёрткой);
`VmState.callTo` — лемма `vm_run` (`IFELSE`, вызов `DICT*GETEXEC`). Время доказательств кошельков не
изменилось. Остаётся: правило цикла не обобщает счётчик `REPEAT`, хранимый в продолжении цикла.

### Порядок работ до 100%

По частоте в реальных кодах (таблица предпроверки) и цене:

0. **Подключить доказанное — сделано** (волна 0, выше): модули с 227 леммами в окружении
   contract-check, `k ≤ globalVersion` из гипотезы, `private`-определения модели, лемма для
   `VmState.callTo`.
1. **Управление из каждого кода FunC**: `CALLREF`/`IFJMPREF`/`IFREFELSE`/`PUSHREFCONT` (сейчас —
   развёрткой; `CALLREF` есть в 11 из 17 кодов), `PUSHCTR`/`POPCTR` для `c5`, `c7`, `*XARGS`,
   `RETALT`, `TRYARGS` и исключение внутри `TRY`, циклы `BRK`, счётчик `REPEAT` в правиле цикла, цикл в
   цикле.
2. **Словари в данных**: `LDDICT`/`STDICT`/`PLDDICT`, `DICT*GET/SET/DEL/REPLACE/ADD` на неизвестном

   `GETNEXT/PREV/MIN/MAX/REMMIN`, формы `OPTREF`.
